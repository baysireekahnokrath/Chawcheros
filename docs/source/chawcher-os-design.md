## 1. แนวคิดหลัก: สายพาน ไม่ใช่ตู้เอกสาร

ระบบทั่วไปให้คนกรอกข้อมูลเข้าไปเก็บ แล้วใครอยากได้ก็ไปค้นเอา — ผลคือไม่มีใครกรอก เพราะกรอกแล้วตัวเองไม่ได้อะไร

ระบบนี้ทำกลับด้าน:

> **แต่ละคนแตะข้อมูลจุดเดียว — จุดที่ตัวเองรู้ดีที่สุดและรู้เป็นคนแรก
> แล้วข้อมูลนั้นไหลไปโผล่เป็น "งานวันนี้" ของคนถัดไปโดยไม่มีใครต้องพิมพ์ซ้ำ**

กฎที่ตามมา: **ข้อมูลหนึ่งชิ้น มีเจ้าของคนเดียว** ที่อยู่ลูกค้ากรอกที่เดียวตอนขาย จัดส่งไม่ต้องพิมพ์ใหม่ สถานะสินค้าคลังเป็นคนอัปเดต ขายไม่ต้องเดา

ถ้าที่ไหนต้องพิมพ์ซ้ำ แปลว่าออกแบบผิด ให้กลับมาแก้

## 3. ใครเป็นเจ้าของข้อมูลอะไร

| แผนก | **เขียน** (เจ้าของ แตะแค่นี้) | **อ่าน** (ระบบยกมาให้ ไม่ต้องหา) |
|---|---|---|
| **คลัง** | ตัวสินค้าอยู่ไหน · สถานะ · ยืม-คืน · ตำหนิ | ออเดอร์ที่ต้องเตรียม |
| **ขาย** | ท่อการขาย · นัด · ผลการคุย · ปิด/ไม่ปิด | สต็อกรายตัว · ราคา · ผ้า · ระยะผลิต · ประวัติลูกค้า |
| **CS** | ข้อสรุปการคุย · ปัญหา · เคสที่ต้องตาม | สถานะส่ง · สต็อก · ประวัติซื้อ · เงื่อนไขรับประกัน |
| **จัดส่ง** | วันส่ง · สถานะ · ปัญหาหน้างาน · หลักฐานส่ง | ออเดอร์ · ที่อยู่ · ขนาด/น้ำหนัก · เบอร์ติดต่อ |
| **การตลาด** | แคมเปญ · คอนเทนต์ · โปรโมชั่น | สินค้า · สเปกที่ยืนยันแล้ว · รูป · ยอดขายรายรุ่น · กลุ่มลูกค้าเก่า |
| **กราฟิก** | ไฟล์งาน · สถานะงาน | บรีฟ · สเปก · รูปสินค้า · design system |
| **เจ้าของ** | ราคา · อนุมัติ · ทิศทาง | ทุกอย่าง + ต้นทุนและกำไร |

**เกณฑ์ตัดสินว่าใครเป็นเจ้าของ: ใครรู้เรื่องนี้เป็นคนแรก และรู้แน่ที่สุด** คลังรู้ก่อนว่าโซฟาตัวนั้นถูกยกออกไป จัดส่งรู้ก่อนว่าส่งไม่ได้เพราะลิฟต์ไม่พอ

## 4. หน้าจอของแต่ละคนคือ "งานวันนี้" ไม่ใช่ฐานข้อมูล

ทุกแผนกเปิดมาเจอ **รายการที่ต้องลงมือ** ไม่ใช่ตารางให้ค้นหา

- **คลัง** — ต้องเตรียมส่งวันนี้กี่ตัว · ของที่ยืมออกไปเลยกำหนดคืนแล้วกี่ตัว · ตัวที่ตำหนิรอตัดสินใจ
- **ขาย** — นัดวันนี้ · คนที่เงียบเกิน 3 วันยังไม่ปิด · ใบเสนอราคาที่ยังไม่ตอบกลับ
- **CS** — เคสที่ค้างเกิน 24 ชม. · ลูกค้าที่ถามเรื่องของที่ยังไม่ส่ง
- **จัดส่ง** — คิววันนี้ · ของที่เลยกำหนดส่ง
- **การตลาด** — งานที่ค้าง · กลุ่มลูกค้าเก่าที่ครบ 12-24 เดือนเดือนนี้
- **เจ้าของ** — 3 ตัวเลข: นัดกี่คน / มาจริงกี่คน / ปิดได้กี่คน + รายการที่รอคุณตัดสินใจ

หน้าจอไหนที่เปิดแล้วไม่มีอะไรต้องทำ แปลว่าไม่ควรมีหน้านั้น

## 5. ชั้น AI — ปุ่ม "ให้ AI ทำให้"

นี่คือส่วนที่ทำให้ระบบนี้ต่างจากระบบสำเร็จรูปที่ซื้อได้ทั่วไป

**ทุกหน้าจอมีปุ่มขอให้ AI ผลิตงาน และ AI อ่านข้อมูลจริงจากระบบเอง — ไม่ถามซ้ำสิ่งที่ระบบรู้อยู่แล้ว**

| ใครกด | ขออะไรได้ | AI ดึงอะไรไปใช้เอง |
|---|---|---|
| **ขาย** | ร่างใบเสนอราคา · ร่างข้อความตามลูกค้าที่เงียบไป | รุ่น ผ้า ราคา ประวัติการคุย |
| **CS** | ร่างคำตอบลูกค้า · สรุปเคสให้หัวหน้า | ประวัติซื้อ สถานะส่ง สเปกสินค้า |
| **จัดส่ง** | ร่างข้อความแจ้งลูกค้าว่าของถึงเมื่อไหร่ | ออเดอร์ คิวส่ง ที่อยู่ |
| **การตลาด** | ร่างโพสต์/โปรโมชั่น · เลือกกลุ่มลูกค้าเก่าที่ควรทักเดือนนี้ | สเปกที่ยืนยันแล้ว ยอดขาย ประวัติลูกค้า |
| **กราฟิก** | ร่าง art direction brief | design system สเปกสินค้า |
| **คลัง** | สรุปของที่ค้างและเลยกำหนดคืน | ตำแหน่งและสถานะตัวสินค้า |

**กฎของชั้น AI — ห้ามยืดหยุ่น:**

1. **AI ร่าง คนส่ง** ห้ามส่งข้อความถึงลูกค้าเองโดยไม่มีคนกด
2. **ห้ามแต่งข้อมูล** ถ้าสเปกไม่มีในระบบ ให้เขียนว่าไม่มี ห้ามเดา
3. **งานที่ผลิตต้องผูกกลับกับ record ที่มันมาจาก** ตามรอยได้เสมอว่าใครขออะไร ตอนไหน ได้อะไรไป
4. **ห้ามแตะเรื่องเงินและการเผยแพร่** ลดราคา อนุมัติ ขึ้นเว็บ = คนทำ
5. AI อ่านฐานเดียวกับคน — ไม่มีฐานแยกของ AI

## 6. อะไรระบบทำเอง อะไรคนต้องบอก

**เกณฑ์:** ถ้าคำนวณได้จากข้อมูลที่มีอยู่แล้ว → ระบบทำเอง ห้ามมีช่องให้กรอก
ถ้าเป็นเหตุการณ์ในโลกจริงที่ระบบมองไม่เห็น → คนต้องบอก

### คนต้องบอก (ระบบไม่มีตา)

| สิ่งที่ต้องบอก | ใคร |
|---|---|
| ยกโซฟาตัวนี้ออกจากคลังไปโชว์รูมแล้ว | คลัง |
| ตัวนี้มีรอยตำหนิ | คลัง |
| คุยกับลูกค้าแล้ว เขาบอกว่า... | ขาย / CS |
| ส่งของถึงแล้ว / ส่งไม่ได้เพราะลิฟต์ไม่พอ | จัดส่ง |
| ลูกค้าเลือกผ้าตัวนี้ ขนาดนี้ | ขาย |
| อนุมัติ / ไม่อนุมัติ | เจ้าของ |

ทุกอันต้องเป็นการกดไม่เกิน 3 ครั้ง ไม่ใช่การกรอกฟอร์ม

### ระบบทำเอง — ห้ามมีช่องให้คนแก้

| ระบบสรุปเอง | คำนวณจาก |
|---|---|
| ของพร้อมขายกี่ตัว | นับตัวที่สถานะ "พร้อมขาย" |
| ลูกค้าคนนี้เงียบไปกี่วัน | วันนี้ ลบ วันที่คุยล่าสุด |
| ครบ 12-24 เดือน ควรทักได้แล้ว | วันที่ส่งมอบ |
| ของยืมออกที่เลยกำหนดคืน | กำหนดกลับ เทียบวันนี้ |
| กำไรใบนี้ | ราคาขาย ลบ ต้นทุน |
| เดือนนี้ นัด/มา/ปิด กี่คน | นับจากท่อการขาย |
| ลูกค้าคนนี้ซื้ออะไรไปบ้าง | ออเดอร์ที่ผูกกับเขา |
| แคมเปญนี้ได้ลูกค้ากี่คน | ที่มาของลูกค้า → ออเดอร์ |

**ตัวเลขเหล่านี้ห้ามเก็บเป็นช่องที่แก้ได้เด็ดขาด ต้องคำนวณสดทุกครั้งที่เปิดดู**

เพราะวันที่มีช่อง "จำนวนคงเหลือ" ให้คนพิมพ์ทับได้ คือวันที่ระบบเริ่มโกหก — คนจะแก้ตัวเลขให้ตรงกับที่ตัวเองคิด แทนที่จะไปแก้ที่ต้นเหตุ แล้วอีกสามเดือนจะไม่มีใครเชื่อตัวเลขไหนอีก

### เส้นที่สาม: ระบบเดาให้ คนยืนยัน

ระบบต้องเติมค่าให้ก่อน แล้วให้คนกดยืนยันหรือแก้ — ห้ามปล่อยช่องว่าง

- วันส่งที่คาดว่าจะถึง (จากระยะผลิต) → จัดส่งยืนยัน
- ราคาจากตัวประกอบ → ขายยืนยันก่อนส่งใบเสนอราคา
- กลุ่มลูกค้าเก่าที่ควรทักเดือนนี้ → การตลาดคัดออกได้

**ทุกครั้งที่คนแก้ค่าที่ระบบเดาไว้ ต้องเก็บไว้ว่าแก้เป็นอะไร** พอสะสมพอจะรู้ว่าสูตรผิดตรงไหน แล้วแก้ที่สูตร — ระบบจะแม่นขึ้นเองโดยไม่ต้องมีใครมานั่งจูน

## 7. สต็อกต้องนับเป็น "ตัว" ไม่ใช่ "จำนวน"

"Kiwi ผ้าเทา มี 4 ตัว" ใช้ไม่ได้ เพราะแต่ละตัวมีชะตาชีวิตต่างกัน

| ช่อง | ตัวอย่าง |
|---|---|
| รหัสตัว | KW-0042 |
| SKU | 104.228.60 |
| อยู่ที่ไหน | คลัง · โชว์รูมเจริญนคร · ยืมออก (ชื่อ/สถานที่) |
| สถานะ | พร้อมขาย · จองแล้ว · ตำหนิ · ยืมออก · ส่งแล้ว |
| ออกไปเมื่อไหร่ | 12 ส.ค. 2026 |
| **กำหนดกลับ** | 12 พ.ย. 2026 |

**ช่อง "กำหนดกลับ" คือช่องที่ทำเงิน** — ของที่ยืมไปโชว์แล้วไม่มีใครตามคืน คือสินค้าที่จมอยู่ในมือคนอื่นโดยไม่มีใครรู้ ระบบต้องเด้งเตือนเมื่อเลยกำหนด

**การย้ายของต้องง่ายกว่าการไม่ย้าย** — สแกน QR บนตัวสินค้า เลือกปลายทาง จบใน 3 วินาที ถ้าต้องเปิดคอมกรอกฟอร์ม จะไม่มีใครทำ และข้อมูลจะเน่าภายในเดือนเดียว

## 8. สิ่งที่ตั้งใจไม่สร้าง

**กล่องข้อความรวม Line/Messenger/IG/Shopee — ซื้อ อย่าสร้าง**
แต่ละแพลตฟอร์มเปลี่ยนกติกาปีละหลายครั้ง วันที่ Meta หรือ Shopee เปลี่ยนระบบ กล่องจะพังกลางวันทำงานและไม่มีใครซ่อมได้ มีเครื่องมือในไทยที่ทำเรื่องนี้เป็นธุรกิจหลัก

**สิ่งที่เราสร้างคือสายเชื่อมเส้นเดียว:** CS คุยจบ กดปุ่มเดียวบันทึกข้อสรุปเข้าประวัติลูกค้า — บทสนทนาอยู่ในเครื่องมือของมัน แต่**ข้อสรุปและประวัติการซื้ออยู่กับเรา**

ไม่สร้างเช่นกัน: ระบบ HR · ระบบบัญชีเต็มรูปแบบ · แชทภายใน · ระบบอนุมัติหลายชั้น · แอปมือถือแยก

## 9. ลำดับการสร้าง

เรียงตาม "ตอนนี้เสียเงินหรือเสียเวลาตรงไหนมากที่สุด"

| ช่วง | สร้างอะไร | ปลดล็อกใคร |
|---|---|---|
| **1-2** | ฐานข้อมูล + ล็อกอิน + สิทธิ์ 4 ระดับ + **สต็อกรายตัว** | คลัง |
| **3-4** | ลูกค้า + ท่อการขาย + นัดหมาย + ประวัติการซื้อ | ขาย, CS |
| **5-6** | สินค้า + **คลังผ้าพร้อมรูป** + **ชั้น AI ตัวแรก (ขาย)** | ขาย, การตลาด |
| **7-8** | ใบเสนอราคา + ออเดอร์ + กำไรต่อใบ | ขาย, เจ้าของ |
| **9-10** | จัดส่ง + ชั้น AI ของ CS และการตลาด | จัดส่ง, CS |
| **ต่อไป** | พาร์ทเนอร์ → โรงงาน/BOM → บริการหลังการขาย | — |

**ชั้น AI ต้องมาตั้งแต่ช่วง 5-6 ไม่ใช่ทิ้งไว้ท้ายสุด** — ทำกับแผนกเดียวก่อนให้เห็นว่าใช้ได้จริง แล้วค่อยขยาย ถ้าปล่อยไว้ท้าย มันจะไม่ได้ทำ

## 10. ความเสี่ยง 3 ข้อ

**1. คนไม่อัปเดต แล้วทุกอย่างปลายน้ำเป็นขยะ**
นี่คือความเสี่ยงที่ฆ่าระบบแบบนี้บ่อยที่สุด ป้องกันด้วยการทำให้การอัปเดต**ง่ายกว่าการไม่อัปเดต** (สแกน QR ไม่ใช่กรอกฟอร์ม) และทำให้คนที่กรอก**ได้ประโยชน์เอง**ทันที ไม่ใช่กรอกให้คนอื่นใช้

**2. ระบบสะท้อนวิธีทำงานที่ยังไม่มีอยู่จริง**
ตอนนี้ยังไม่มีกระบวนการที่เขียนไว้ ระบบจะไปบังคับให้มี ซึ่งดี — แต่ต้องยอมรับว่าจะต้องแก้หลังใช้จริง 2-3 รอบ อย่าออกแบบให้สมบูรณ์แบบตั้งแต่แรก

**3. กินเวลาเจ้าของ 2-3 เดือนในเดือนที่โชว์รูมยังว่าง**
ให้ Claude Code สร้างไป Bay เข้ามาเฉพาะตอนมันถามจริงๆ ห้ามนั่งคุมทุกขั้น — เวลาของ Bay ควรอยู่ที่การพาคนเข้าร้านและงานพาร์ทเนอร์

## 11. สิ่งที่ยังไม่รู้ ต้องเติมก่อนเริ่มสร้าง
