# ข้อ 4 — บอกตรงๆ ว่าอะไรทำไม่ได้ แพงเกินคุ้ม หรือควรซื้อมากกว่าสร้าง

พี่บอกว่าอยากรู้ก่อนเริ่ม ไม่ใช่รู้ตอนทำไปครึ่งทาง — นี่คือทุกอย่างที่ผมเห็น

---

## 🔴 เรื่องที่จะทำให้ช้าหรือพัง ถ้าไม่จัดการก่อน

### 1. คอขวดตัวจริงไม่ใช่โค้ด — คือการตัดสินใจ 1,012 แถว

พี่เพิ่งบอกผมว่า **"จริงๆ ทั้งหมด คือ ยังไม่มี SKU"** ซึ่งเปลี่ยนขนาดงานไปเลย

ก่อนหน้านี้ผมเข้าใจว่าขาด 548 จาก 1,012 — ความจริงคือ **ขาดทั้ง 1,012 แถว**
เลขที่มีอยู่เป็นของ NocNoc ที่ปิดกิจการไปแล้ว

แปลว่ามีคนต้องนั่งดูทีละแถว แล้วตอบว่า:
- ยังขายอยู่ไหม
- แถวนี้กับแถวโน้นคือตัวเดียวกันหรือเปล่า
- อันนี้เป็น "รุ่น" หรือเป็น "ตัวเลือกของรุ่นอื่น"

**ระบบช่วยไม่ได้ ผมช่วยไม่ได้ AI ช่วยไม่ได้** — เพราะมันคือความรู้ที่อยู่ในหัวคน
ผมช่วยได้แค่จัดกลุ่มมาให้ล่วงหน้าเพื่อให้ตัดสินใจทีละ*กลุ่ม*แทนทีละ*แถว*

> **คำแนะนำ:** ถ้าพี่ทำเองคนเดียว เผื่อเวลาไว้ 2-3 สัปดาห์
> และผมแนะนำให้เริ่มจาก **50 รุ่นที่ขายดีที่สุด** ก่อน ไม่ต้องครบ 1,012 ถึงจะเริ่มใช้ระบบได้
> ที่เหลือทยอยเติม — **อย่าให้ตัวเลข 1,012 เป็นเหตุผลที่ทำให้ไม่ได้เริ่มสักที**

### 2. จำนวน SKU อาจระเบิด ถ้าตัดสินใจผิดตรงเดียว (OPEN-2)

พี่อธิบายว่าตัวเลือกซ้อนกันเป็นชั้น: ขนาด → ประเภทผ้า → สีผ้าย่อยๆ ลงไปอีก

ลองคิดเลขดู — Emu Sofa ตัวเดียว:
```
3 ขนาด × (ผ้า A 20 สี + ผ้า B 15 สี + หนัง 10 สี)  =  135 SKU
```
**โซฟารุ่นเดียว 135 SKU** ถ้ามี 50 รุ่น = มากกว่า **6,000 SKU**
จากที่ตอนนี้มี 1,012 แถว → งานกรอกข้อมูลเพิ่มขึ้น 6 เท่า

**ข้อเสนอของผม:** SKU อยู่ที่ระดับ **รุ่น + ขนาด + เกรดวัสดุ** → Emu Sofa เหลือ **12 SKU**
ส่วนสีผ้าที่ลูกค้าเลือก ไปบันทึกที่ **ออเดอร์** กับที่ **ตัวสินค้าจริง**

เหตุผล:
- **ราคาเท่ากันทั้งเกรด** อยู่แล้ว ผ้าเกรด A สีเขียวกับสีน้ำเงินราคาเดียวกัน → ไม่ต้องแยก SKU
- ของจริงแต่ละตัวต้องบันทึกผ้าจริงอยู่แล้วในตาราง `stock_units`
- **เพิ่มสีผ้าใหม่ = เพิ่ม 1 แถวในตารางวัสดุ** ไม่ต้องไปสร้าง SKU ใหม่อีก 50 ตัว

⚠️ แต่นี่เป็นเรื่องโครงสร้างธุรกิจ **ผมไม่ตัดสินใจเอง** — พี่ยืนยันมา

### 3. ต้นทุนที่เคยเห็นกันทั้งทีม จะเห็นไม่ได้อีก

วันนี้ทั้งไฟล์ Stock (Landing Cost, Inventory Value) และ Order Tracking (ต้นทุน)
เปิดดูได้โดยคนที่เข้าถึงไฟล์ พอย้ายเข้าระบบแล้วล็อก **คนที่เคยเห็นจะเห็นไม่ได้**

**เรื่องนี้กระทบคน ไม่ใช่กระทบระบบ** ควรบอกทีมล่วงหน้าว่าเป็นการจัดระเบียบ
ไม่ใช่การไม่ไว้ใจใคร

### 4. การใช้คู่กันสองระบบ มีต้นทุนซ่อนอยู่ — และผมขอแก้วิธีนิดนึง (OPEN-6)

พี่บอกว่าอยากใช้ Google Sheets คู่กันเป็น backup sync ทุกตีสอง — **เห็นด้วย** แต่มีกับดัก

| แบบ | เกิดอะไรขึ้น | ราคา |
|---|---|---|
| **ทางเดียว: ระบบ → Sheets** ✅ | ชีทเป็นภาพสะท้อนอ่านอย่างเดียว ระบบเป็นความจริงเสมอ | ถูก ปลอดภัย |
| **สองทาง: แก้ที่ชีทได้ด้วย** ❌ | วันหนึ่งจะมีคนแก้ทั้งสองที่ในวันเดียวกัน แล้ว**ไม่มีใครรู้ว่าอันไหนถูก** | แพง และพังแน่นอน |

ผมขอทำแบบ**ทางเดียว** และจะ**ล็อกชีท backup ให้แก้ไม่ได้** ไม่งั้นวันหนึ่งจะมีคนเผลอแก้ที่ชีท
แล้วงงว่าทำไมระบบไม่เห็น

> ถ้าพี่ตั้งใจให้แก้ที่ชีทได้ด้วยจริงๆ บอกผมก่อนนะครับ **ราคาและความเสี่ยงคนละเรื่องเลย**

### 5. ต้องเดินติดป้ายของจริงทั้งคลัง

การนับเป็นตัวไม่ได้เกิดจากโค้ด — เกิดจากมีคนเดินไปติดสติกเกอร์ทีละชิ้น
ของกี่ร้อยชิ้นก็กี่ร้อยครั้ง **ตรงนี้ไม่มีทางลัด**

ข่าวดี: ทำคู่ขนานกับการเขียนโปรแกรมได้ พอพิมพ์ป้ายได้ก็เริ่มติดเลย

## 🟡 ควรซื้อ ไม่ควรสร้าง

### 6. ใบกำกับภาษี / งานบัญชี — **ซื้อ**

ในไฟล์พี่มี "ใบกำกับ/ใบชมพู" อยู่แล้ว การสร้างระบบใบกำกับภาษีให้ถูกกฎหมายไทย
(e-Tax Invoice, รูปแบบที่สรรพากรรับ, การเก็บย้อนหลัง) เป็นงานที่**มีคนทำไว้ดีแล้วและถูกกว่ามาก**

**แนะนำ:** PEAK หรือ FlowAccount (หลักพันต่อเดือน) แล้วให้ Chaw Cher OS ส่งข้อมูลออเดอร์ไปให้
**สร้างเองไม่คุ้ม และถ้าทำผิดกฎหมายภาษีคือเรื่องใหญ่**

### 7. เครื่องยิงเลเซอร์ + ซอฟต์แวร์ที่มากับเครื่อง — **ซื้อ**

ตามที่พี่บอกว่าจะหาเครื่องมา — ถูกต้องแล้ว เครื่องพวกนี้มาพร้อมซอฟต์แวร์ของมันเอง
**Chaw Cher OS แค่ออกเลข Serial ให้ แล้ว export ไฟล์ไปเข้าเครื่อง** ไม่ต้องเขียนโปรแกรมยิงเลเซอร์

### 8. เครื่องพิมพ์ sticker — **ซื้อ**

Brother หรือ Zebra ตัวละไม่กี่พัน ระบบแค่สร้างไฟล์ป้ายให้
**ไม่ต้องเขียนโปรแกรมออกแบบป้าย** เสียเวลาเปล่า

### 9. อ่านสลิปโอนเงินอัตโนมัติ — **ยังไม่ต้องทำ**

API ธนาคารไทยสำหรับ SME เข้าถึงยากและแพง ส่วน OCR อ่านสลิปก็ผิดพอที่จะต้องมีคนตรวจอยู่ดี

พี่บอกเองว่าบัญชีเป็นคนเช็คยอดเงินเข้า → **ให้บัญชีอัปโหลดสลิปแล้วกดยืนยัน** พอแล้ว
ใช้เวลาต่อครั้งไม่กี่วินาที และมีคนรับผิดชอบชัดเจน ซึ่งดีกว่าระบบที่เดาเอง

## 🟢 เรื่องที่ผมว่าคิดถูกแล้ว

- **Supabase + Next.js + Vercel** — ขนาดกำลังพอดี ไม่เล็กไป ไม่ใหญ่เกิน ค่าใช้จ่ายหลักร้อยถึงพันต่อเดือน
- **ห้าม DELETE** — ถูกมาก ธุรกิจเฟอร์นิเจอร์มีออเดอร์ยาวหลายเดือน ประวัติสำคัญกว่าความสะอาด
- **ตัวเลขคำนวณได้ ห้ามเก็บ** — ข้อนี้ดีที่สุดในทั้งหมด ไฟล์เดิมมี Balance ที่คนพิมพ์เอง ซึ่งวันหนึ่งจะผิดแน่
- **แยกรุ่นออกจากตัวที่ขายจริง** — ถูกต้อง และไฟล์ v3 ก็มีคอลัมน์ parent/variant เตรียมไว้แล้ว
- **ไม่ผูก BOM ตอนนี้** — ถูก BOM คือ scope ที่ใหญ่ที่สุดและเป็นงาน ASE
- **มือถือมาก่อน** — ถูก คนใช้จริงคือเซลส์ในงานแสดงกับคลังที่เดินไปเดินมา ไม่มีใครนั่งโต๊ะ

## 🔵 สองข้อเสนอที่ผมอยากขอแก้จากที่พี่เขียนมา

### ก. สถานะออเดอร์ — ขอแยกเป็น 3 เส้น (OPEN-5)

พี่ให้มาเป็นเส้นเดียว 8 สถานะ ปัญหาคือมันเอา**เรื่องเงิน**กับ**เรื่องของ**มาต่อกันในเส้นเดียว
แล้วพอเจอเคสจริงของพี่เองก็แทนไม่ได้:

- พี่บอกว่ามีเคส **"ส่งก่อน จ่ายทีหลัง"** → เส้นเดียวจะเดินถอยหลังจาก "ส่งสำเร็จ" กลับมา "ยังไม่จ่าย" ไม่ได้
- พี่บอกว่า **1 ออเดอร์ส่งได้หลายครั้ง** → "ส่งสำเร็จแล้ว" จริงครึ่งเดียวได้ยังไง

**ขอเสนอ 3 เส้นแยกกัน วิ่งพร้อมกันได้:**

| เส้น | ค่าที่เป็นไปได้ | ใครดู |
|---|---|---|
| **ออเดอร์** | เปิดออเดอร์ · กำลังดำเนินการ · ปิดงาน · ยกเลิก | ทุกคน |
| **เงิน** *(คำนวณสด ไม่มีใครพิมพ์)* | ยังไม่จ่าย · มัดจำแล้ว · จ่ายครบ | บัญชี |
| **การส่ง** *(แยกรายเที่ยว)* | รอของ · พร้อมส่ง · รอนัด · นัดแล้ว · ส่งแล้ว | คลัง + เซลส์ |

ได้ครบทุกสถานะที่พี่เขียนมา แต่**เคสพิเศษของพี่เองก็บันทึกได้ด้วย**
และเส้น "เงิน" ไม่มีใครพิมพ์ได้เลย — ระบบคำนวณจากเงินที่รับจริง ตรงกับกฎข้อ A10

### ข. "ติดตามเพื่อนัดส่ง ครั้งที่ xx" ไม่ควรเป็นสถานะ

ถ้าเก็บเป็นสถานะ พอติดตามครั้งที่ 4 **ข้อมูลครั้งที่ 1-3 หายหมด**
ทั้งที่นั่นคือข้อมูลที่มีค่าที่สุด (โทรไปกี่ครั้ง ลูกค้าว่ายังไง ติดตรงไหน)

**ขอเก็บเป็นตารางบันทึกการติดตามแทน** — ทุกครั้งที่โทรเพิ่ม 1 แถว
แล้วเลข "ครั้งที่ 4" ก็แค่นับแถวเอา ไม่ต้องมีใครพิมพ์ และไม่มีวันผิด
