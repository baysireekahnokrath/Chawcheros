## ขั้นตอนที่อยู่ · Bay ตอบ 2026-10-29

> ขั้นตอน เก็บข้อมูล งานที่เสร็จ พร้อมส่งลูกค้า

**ไม่ใช่ QC ระหว่างผลิต — เป็นการบันทึกของที่ผลิตเสร็จแล้ว ก่อนออกจากโรงงาน**

เปลี่ยนความหมายของงานนี้ไปเลย จาก "ขอให้ช่วยดูงานหน่อย" เป็น

| สิ่งที่มันเป็นจริงๆ | ใช้ทำอะไรต่อ |
|---|---|
| **หลักฐานสภาพของตอนออกจากโรงงาน** | ลูกค้าบอกว่าของมาถึงแล้วเสียหาย — มีรูปยืนยันว่าออกไปในสภาพไหน |
| **ตัวเชื่อม PO กับของจริงที่ผลิตออกมา** | รู้ว่า PO นี้ได้ของตัวไหนไป รหัสอะไร ใครทำ |
| **สัญญาณว่า "พร้อมส่ง"** | ออฟฟิศเริ่มจัดส่งได้ |

### ✅ ครึ่งหนึ่งมีในระบบแล้ว · โมดูลคลัง (0019)

`stock.units` มีช่องที่ต้องใช้อยู่แล้วครบ

| ช่อง | เก็บอะไร |
|---|---|
| `unit_code` | รหัสของตัวนั้น ออกให้เองอัตโนมัติ (U0000001) |
| `variant_id` | เป็นสินค้าตัวไหน |
| `made_at` · `made_on` · `made_by` | **ผลิตที่ไหน · วันไหน · ใครทำส่วนไหน** |
| `serial_no` | เลขเครื่องถ้ามี |
| `status` · `location_id` | สถานะ · อยู่ที่ไหน |

ในไฟล์เขียนคำพี่ไว้ด้วยว่า *"track back ได้ว่าผลิตที่ไหน วันไหน ใครผลิตส่วนไหนบ้าง"*
และ `stock.receive_units()` ที่รับของเข้าคลังก็ทำงานได้แล้ว

**→ สิ่งที่ขาดคือ 3 อย่างเท่านั้น: รูป · การผูกกับ PO · การส่งเข้า LINE**

### 📌 รูปควรผูกกับ "ตัวสินค้า" ไม่ใช่แค่ PO

| เหตุผล |
|---|
| PO หนึ่งใบมีโซฟา 3 ตัว — "รูปของ PO-0442" ไม่รู้ว่าตัวไหน แต่ "รูปของ U0000123" ชัดเจน |
| คลังนับเป็นตัว ทุกตัวมีรหัสของตัวเองอยู่แล้ว (กฎที่ตกลงกันไว้) — ผูกกับ PO เฉยๆ จะขัดกับโครงที่วางไว้ |
| **B1 ลิงก์สถานะให้ลูกค้า** — ลูกค้าเห็นรูปของตัวที่เป็นของเขาจริงๆ ไม่ใช่รูปรวมของทั้งใบ |
| เคลมความเสียหายเป็นรายตัว ไม่ใช่รายใบ |
| **แคมเปญต้นไม้ ข้อ 8** ที่พี่เขียนไว้ว่าอยากเก็บรายละเอียดของที่ผลิต พร้อมข้อมูลช่าง — ใช้ข้อมูลชุดเดียวกันนี้เลย |

**→ ขั้นตอนถ่ายรูปนี้ ที่จริงคือเหตุการณ์ "ผลิตตัวนี้เสร็จแล้ว" ในโมดูลคลัง
ไม่ใช่โมดูลใหม่ที่แยกไปอยู่ข้างนอก**

### 🔴 2 ช่องว่างที่ต้องปิดก่อน

| # | ขาดอะไร | หนักแค่ไหน |
|---|---|---|
| G1 | **ระบบยังไม่มีที่เก็บไฟล์เลย** — ตรวจแล้วไม่มีถังเก็บรูป ไม่มีนโยบายสิทธิ์ของไฟล์สักอัน | ทำได้ ไม่ยาก แต่เป็นของใหม่ และพันกับเรื่อง URL สาธารณะที่ LINE ต้องใช้ |
| G2 | **ไม่มีตาราง PO / ออเดอร์เลยสักตาราง** | **เป็นตัวบล็อก** — จะ "เลือก PO" ไม่ได้ถ้าไม่มีอะไรให้เลือก |

> G2 ไม่มีทางเลี่ยง เพราะหัวใจของขั้นตอนนี้คือ "พร้อมส่ง**ลูกค้า**"
> ถ้าไม่รู้ว่าลูกค้าไหน รูปที่ถ่ายก็ลอยอยู่เฉยๆ
> **โมดูลออเดอร์คือสิ่งเดียวที่กั้นอยู่ระหว่างพี่กับงานนี้**

## จุดสำคัญที่สุด · "save" กับ "ส่ง LINE" เป็นสองระบบ

ทำให้สำเร็จพร้อมกันทั้งคู่แบบรับประกันไม่ได้ ไม่ว่าเขียนโค้ดเก่งแค่ไหน

| ถ้าทำแบบ | จะได้ปัญหา |
|---|---|
| ส่ง LINE ให้สำเร็จก่อนค่อย save | LINE ล่ม = save ไม่ได้ = **ช่างถ่ายรูปแล้วงานหาย** |
| save แล้วค่อยส่ง LINE แบบยิงทิ้ง | ส่งไม่สำเร็จ = **ไม่มีใครรู้ว่าต้องเช็คงานนี้** |

**วิธีที่ถูก (outbox)**

1. **save ต้องสำเร็จเสมอ** — รูป + PO + คนถ่าย + เวลา ลงระบบก่อน นี่คือต้นฉบับ
2. การส่ง LINE เป็น**งานแยกที่มีสถานะของตัวเอง** — `รอส่ง` · `ส่งแล้ว` · `ส่งไม่ได้`
3. ส่งไม่ได้ก็**ลองใหม่เองอัตโนมัติ** ไม่ต้องให้คนมากดซ้ำ
4. มี**กุญแจกันซ้ำ** (1 รายการ = ส่งได้ครั้งเดียว) → กด save รัวก็ไม่ซ้ำ (แก้ F2)
5. ในแอปเห็นสถานะ → ช่างรู้ว่าส่งถึงแล้วหรือยัง ไม่ต้องเดา
6. ค้างเกิน X นาที = ขึ้นเตือนในระบบ (แก้ F4 · F5 ที่ปกติจะเงียบ)

เข้ากับกฎที่ตกลงกันไว้: **ส่งไม่ได้ = เปลี่ยนสถานะ ไม่ใช่ลบ** · สถานะเป็นของระบบ คนแก้ไม่ได้

สำหรับ F1 สัญญาณ: ถ่ายแล้ว**เก็บในเครื่องก่อน** คิวอัปโหลดเอง เดินออกมาที่มีสัญญาณแล้วขึ้นเอง
ช่างไม่ต้องรอดูหน้าจอ

## ⚠️ ข้อจำกัดของ LINE ที่ต้องรู้ก่อนตัดสินใจ (ตรวจแล้ว 2026-10-29)

### 1 · LINE Notify ตายแล้ว

ปิดบริการ **31 มี.ค. 2025** · ทางเดียวที่เหลือคือ **Messaging API ผ่าน LINE Official Account**
หมายความว่าต้องมี LINE OA และเอาบอทเข้าห้อง ไม่ใช่แค่ขอ token ง่ายๆ เหมือนเมื่อก่อน

### 2 · 💰 คิดเงิน "ต่อคนในห้อง" ไม่ใช่ "ต่อข้อความ"

**นี่คือเรื่องที่คนพลาดกันมากที่สุด**

เอกสาร LINE บอกเองว่านับตามจำนวนคนที่ได้รับ — ส่ง 1 ครั้งเข้าห้องที่มี 5 คน **นับเป็น 5 ข้อความ**

แพ็กเกจไทย (ยังไม่รวม VAT · ต้องยืนยันกับ LINE for Business อีกครั้ง)

| แพ็กเกจ | ราคา/เดือน | รวมข้อความ | ส่วนเกิน |
|---|---|---|---|
| ฟรี | 0 | **300** | ซื้อเพิ่มไม่ได้ |
| Basic | ฿1,280 | 15,000 | ฿0.10/ข้อความ |
| Pro | ฿1,780 | 35,000 | ฿0.06/ข้อความ |

**ลองคิดจริง · ห้องเช็คงานมี 10 คน**

| ส่งแบบไหน | ต่อวัน | ต่อเดือน | ต้องใช้ |
|---|---|---|---|
| 1 รูป = 1 ข้อความ · วันละ 30 รูป | 300 | 9,000 | Basic |
| ห้องมี 15 คน · วันละ 30 รูป | 450 | 13,500 | Basic (ใกล้เต็ม) |

### 3 · ✅ ช่องที่ประหยัดได้มาก · 1 ครั้งส่งได้ 5 รูป ราคาเท่าเดิม

เอกสาร LINE ระบุว่า**จำนวนรูปในข้อความเดียวไม่มีผลกับการนับ** — นับแค่จำนวนคนที่ได้รับ

> **ส่ง 5 รูปในครั้งเดียว = ราคาเท่ากับส่ง 1 รูป**

| ส่งแบบไหน · ห้อง 10 คน · 10 PO/วัน · PO ละ 5 รูป | ต่อเดือน | ต้องใช้ |
|---|---|---|
| ส่งทีละรูป (50 รูป/วัน) | 15,000 | Basic เต็มพอดี |
| **รวมเป็น 1 ครั้งต่อ PO** (10 ครั้ง/วัน) | **3,000** | Basic เหลือเยอะ |
| **สรุปวันละครั้ง** (1 ครั้ง/วัน) | **300** | ฟรีพอดีเป๊ะ (เสี่ยง) |

**→ ต้องรวมรูปเป็นชุดต่อ PO ตั้งแต่ออกแบบ อย่าส่งทีละรูป**

### 4 · รูปต้องเปิดจาก URL สาธารณะ

LINE รับแต่ **JPEG/PNG** (ไม่รับ HEIC) · ต้องมี 2 URL (รูปเต็ม ≤10 MB · รูปย่อ ≤1 MB) และต้องเป็น https ที่ LINE เข้าถึงได้

**ขัดกับที่เราล็อกข้อมูลไว้หมด** — ระบบเราตอนนี้คนไม่ล็อกอินเข้าไม่ถึงอะไรเลยสักตาราง
แต่ LINE ต้องเข้าถึงไฟล์รูปได้

ทางแก้: **URL ชั่วคราวที่หมดอายุเอง** (signed URL) ไม่ใช่เปิดถังรูปให้สาธารณะ
ต้องเผื่อว่า LINE แคชรูปไว้ อายุ URL สั้นเกินก็ไม่ขึ้น

## ทางเลือกที่ควรชั่งน้ำหนัก

| แบบ | ข้อดี | ข้อเสีย |
|---|---|---|
| **ส่งรูปเข้า LINE ตรงๆ (เป็นชุดต่อ PO)** | เห็นรูปในห้องทันที ไม่ต้องกดอะไร · เหมือนที่ทำกันอยู่ | เปลือง (3,000/เดือน) · ต้องเปิด URL ชั่วคราว · ลบไม่ได้ถ้าส่งผิด |
| **ส่งลิงก์เข้าหน้าเช็คงานในระบบ** | ถูกกว่า · ข้อมูลอยู่ในระบบ · ส่งผิดก็แก้ที่หน้าได้ · เห็นว่าใครเปิดดูแล้ว | ต้องกดลิงก์ ต้องล็อกอิน — **คนจะขี้เกียจกด** |
| **ส่งรูปย่อ 1 รูป + ลิงก์ดูทั้งหมด** | เห็นภาพพอให้รู้ว่างานอะไร แล้วค่อยกดดูละเอียด | ซับซ้อนขึ้นเล็กน้อย |

**ความเห็นผม:** แบบที่ 3 · ในห้อง LINE ยังเห็นรูปเลยทันที (ซึ่งเป็นเหตุผลที่ LINE เวิร์ค)
แต่รายละเอียดครบและแก้ไขได้อยู่ในระบบ และไม่ต้องยิงรูป 50 รูปขึ้น LINE ทุกวัน
